# Implementation review and deployment corrections

Date: 2026-09-17. Scope: extras-only runtime, actual Klippy integration, and
the deployed single-FPS OpenAMS macros. No tracked Klipper source was changed.

## Findings corrected

1. Managed macro status used Klipper's cached wrapper: a real macro observed
   `[0, 0]` across a status-changing command. The adapter now supplies the live
   wrapper and the regression observes `[0, 1]`.
2. Cancellation/failure could allow later commands inside legacy helpers and
   queued template actions. Admission checks now guard each boundary and queued
   callback, and paused managed macros cannot spawn. Cleanup remains available
   through narrowly scoped native recovery and virtual-SD error handlers.
3. Complete API scripts could execute their prefix before detecting an unclosed
   block, and overlapping submissions created runs before owning the mutex.
   Complete preflight and serialized run creation now precede execution.
4. Virtual-SD's global source flag could misclassify unrelated API/child input.
   Real worker greenlets and bound source identity now determine ownership.
   Implicit EOF joins use the file's run, preserve error status, invoke configured
   cleanup, and cannot report success after a dependency failure.
5. Ordinary print lines accumulated toward a 2 MB block limit, and completed
   runs accumulated indefinitely. Limits are now per captured block and bounded
   to 64 recent runs, without evicting active/unwinding contexts.
6. Helper return replies could leak their last device subcommand's reply.
   Replies now belong to command frames; status/result snapshots are detached.
7. Jinja `with` output was discarded and child namespaces could share mutable
   locals. Both are corrected. Unsupported inline statements and output-producing
   filter/call blocks fail clearly before execution; legacy templates are unchanged.
8. The rewritten standalone unload omitted OAMS transport. It now completes
   unloading, refreshes sensor/driver observations between phases, and aborts
   subsequent toolchanges on failure. Only loading overlaps nozzle cleaning.
   The previously active 150 mm unload assist is restored; homed/heated/unpaused
   and group guards precede hardware commands. Optional sensors remain disabled.

These are code findings and reproduced test mechanisms, not claims that the
printer physically experienced each failure.

## Remaining limits

The initial OAMS MCU connection error was reproduced with the original
configuration and later cleared when the board became available. A supervised
T0 workflow was subsequently attempted twice. Both attempts reached the OAMS
transport boundary described below and stopped safely; a successful physical
toolchange and a multi-lane sequence remain outstanding.

Managed macros with children cannot execute inside another child. In particular,
invoke the supplied `T0`–`T3` from the default routine. Commands share the real
motion planner and hardware; software cancellation does not prove physical stop.
Geometry, material tuning, driver cancellation, and physical sensor behavior
still require supervised hardware checks.

## Live availability follow-up

After the OAMS board became available, Klipper reached `ready`, CAN discovery
reported UUID `66e4a3d0cd57`, and the controller produced live Hall/FPS telemetry.
All revised macros and the `gco_routines` object were present. A no-motion live
program completed successfully: its `live_probe` child executed `RESPOND`, the
default routine completed `WAIT ON=live_probe`, and both retained empty results
with no run fault while `print_stats` remained `standby`.

That inspection revealed that the printer deliberately sets Klipper
`min_extrude_temp: 10`, making `can_extrude=true` at room temperature. The macros
now independently require at least 170 C (configurable as
`minimum_extrude_temperature`) before toolhead extrusion, cutting, or transport.
Tests cover both toolchange and standalone-unload rejection when `can_extrude`
is true at 23 C.

The first live cold rejection also exposed a case mismatch in the configured
group preflight: tool commands intentionally remain `T0`–`T3`, but live
`configfile.settings` stores section keys as `filament_group t0`–`t3`. The
lookup now lowercases only its settings key while preserving uppercase driver
values. Tests use the real normalized status shape.

The corrected macro was staged through the Pi smoke again, backed up, installed,
and loaded after Klipper returned to `ready`. A live `T1` request at 22.97 C with
an unhomed toolhead then failed with the intended homed/heated/unpaused error.
Before and after, the toolhead position was `[0, 0, 0, 0]`, `current_group` and
`current_spool` were null, `print_stats` was `standby`, and the printer was not
paused. No load, unload, extrusion, or toolhead move was admitted.

The additional pre-follow-up macro is recoverable from
`/home/pi/gco-routines/backups/live-20260917/temperature-guard/oams_macros.cfg`.
The intermediate temperature-guard revision that still had the settings-key
case mismatch is retained beside it as `oams_macros.invalid-group.cfg` for audit;
it should not be used for rollback.

Two hardware diagnostics remain outside the routine-plugin correction: RFID
reader B reports `soft reset timed out (CommandReg=0xff)`, while reader A
initializes as version 0xA1. The proprietary OAMS firmware also exposes a rapidly
increasing `tx_retries` counter despite `rx_error=0`, `tx_error=0`, active
telemetry, and a ready printer. Those observations should be resolved or
understood before a long torture test; they did not fault the no-motion probe.

## Supervised T0 transport attempts

With the existing printer, homing, and macro configuration treated as
authoritative, T0 was attempted twice at the printer's established 260 C ABS
toolchange temperature. The two attempts followed the same observable pattern:

- the encoder advanced from approximately 3 clicks to 2237/2254 clicks;
- T0's hub Hall sensor asserted;
- the manager's one-second encoder deltas fell through 2 to 0;
- `_monitor_load_speed` paused the printer and firmware returned operation code
  6, `Spool loading cancelled`;
- `OAMSM_LOAD_FILAMENT` returned without raising, but `current_group` remained
  null; and
- the revised `_TX` state check detected that mismatch, skipped final toolhead
  extrusion and all later lanes, paused, and raised the intended toolchange
  error.

The repeatable stop near the configured 2062-click PTFE length, after the hub
sensor asserted, favors the physical slide/buffer FPS path or its OAMS
firmware/manager handoff over a gco-routines scheduling failure. The OAMS-side
FPS telemetry stayed approximately zero during the attempts. After recovery,
the separate `[fps]` object was alive and centered at 0.4994, so the two signal
paths should not be treated as the same observation. The camera covers the bed
and toolhead, not the buffer assembly, and therefore could not visually confirm
slide travel. The trace does not by itself distinguish a real slide/path stop
from a monitor false-positive.

The installed manager declares a failure after two samples whenever a load is
still marked `LOADING` and the encoder changes by less than one click; it does
not exempt an asserted hub sensor or a reached path-length endpoint. The
pre-install macro also called the same blocking `OAMSM_LOAD_FILAMENT` before
toolhead extrusion, so this condition is not introduced by moving that command
into a gco-routines child.

After each attempt, the partial path was recovered with the raw OAMS unload,
errors were cleared, and pause state was cleared. The final observed state was
`standby`, unpaused, heater target 0, XYZ homed, `current_group=null`,
`current_spool=null`, and all hub sensors clear. The first recovery returned the
encoder near 3 clicks. The second overshot zero and exposed the unsigned value
`4294967293` (that is, -3 modulo 32 bits), another OAMS telemetry edge to keep in
mind when reviewing encoder-difference logic. No T1-T3 physical attempts were
made after T0's repeated cancellation.

## FPS revision 2.1 pin correction

The printer's FPS board is hardware revision 2.1. The local production branch
`stm32-rev2.1` at commit `82684ee` routes the `/HES` net to STM32F072 pad 17,
`PA3`; pad 16, `PA2`, is explicitly unconnected. The public OpenAMS
`stepper_follower.cfg` likewise specifies `pin:PA3`. The active printer config
instead had `[fps] pin: fps:PA2`.

The active setting was changed only from `fps:PA2` to `fps:PA3`, with the prior
file backed up as
`/home/pi/printer_data/config/oams.cfg.before-fps21-pa3-20260917`. Klipper
returned to `ready` after `FIRMWARE_RESTART`. The live FPS value changed from a
false, fixed reading near 0.499 on the unconnected PA2 input to approximately
0.0039 on the real PA3 HES input.

One instrumented T0 attempt then sampled PA3 at roughly 10 Hz. Across 148 valid
samples, the FPS value remained between 0.003418803 and 0.004151404. Meanwhile,
the OAMS encoder advanced to 2238 clicks and T0's hub Hall sensor asserted before
the same zero-speed cancellation. This directly supports a slide/buffer-path
fault: the transport reaches the hub/path, but the FPS slide/HES signal does not
move. It does not yet distinguish a mechanically stuck or unengaged slide from
a magnet/sensor/wiring fault. A manual full-travel slide test while observing
PA3 is the next non-transport diagnostic.

The partial feed was unloaded after the instrumented attempt. Final state was
`standby`, unpaused, heater target 0, XYZ homed, no current group or spool, and
all hub sensors clear. No further automatic load should be attempted until the
manual slide test produces a meaningful PA3 range.
